# 房车场景与资源结算设计

本文维护房车作者的场景与结算方案，角色卡及脚本按此处理。DVS 的公共能力见[作者使用手册](https://github.com/q3boy/st-sqlite-helper/blob/master/doc/dvs/指南/DVS作者使用手册.md)。

目标是让变量模型分析正文，记录行程、时长、补给和额外消耗；JS 按固定系数计算油、水、电。结算输入只在本次处理时使用，不进入数据库，也不提供给下一轮正文。

## 正文资料筛选与剧情规划

[卡片索引](../index.yaml)中 DVS 脚本的默认变量开启 `dvs_input_inject` 和 `dvs_plot`。使用已支持输入增强的 DVS 版本，并在 DVS 设置中配置输入增强使用的模型；运行中可通过 `DVS.setInject({ filter, plot })` 调整开关。脚本变量由酒馆保存，更新卡片后的实际开关以 `DVS.getInject()` 读回为准，不在每次启动时覆盖玩家的选择。公共用法见[正文筛选与剧情规划](https://github.com/q3boy/st-sqlite-helper/blob/master/doc/dvs/指南/DVS接口与进阶用法.md#正文筛选与剧情规划)。

| 资料 | 本轮正文的处理 |
| --- | --- |
| [房车基础信息](../世界书/房车基础信息.txt) | 常驻，提供车辆身份、主要空间、尺寸及移动限制；主角外出不改变房车位置 |
| [房车详细设定](../世界书/房车设定.txt) | 本轮已明确安排或必要过程涉及驾驶、返回、使用车辆或车旁互动时保留；已有具体关联但细节未知时保留，不凭未安排的后续情节保留 |
| [当前状态](../世界书/DVS-NAR_data.txt)中的房车物资、随身物品 | 四段宏按“本轮相关”组选择本轮已明确安排或必要过程所需的已有物品；已有具体关联但细节未知时保留，随身物品按持有人与物品名共同定位 |
| 角色信息 | [作者脚本](../脚本/DVS.js)的 `narrativePrepare` 先生成关系阶段，保持原有好感度、相遇情境和未知值的正文处理；仅当同行状态为“已离开”时裁减为姓名、年龄、身份、生活背景、关系阶段、对主角观感和同行状态 |
| 去AI味 | 使用 `[DVS_FILTER_SKIP]`，纯文风和行文检查只进入正文，不占用筛选与规划输入；写作规范含时空、车辆状态和资源限制，仍保留供规划参考 |

字段裁减只改变正文准备副本，筛选与规划模型也读取这份副本。原始角色表和变量更新的 `beforeGen` 仍保留完整记录；同行、未加入或未知状态均不按离开处理。物品筛选只选择已有记录，未选中不代表禁止新增物品，正文实际发生后仍由变量模型独立更新。关闭输入增强时输出全部准备物品，已离开角色的固定字段裁减仍生效。

[旅行与日常规划](../世界书/DVS-PLOT.txt)按“本轮方向、情节步骤、事实与边界、结束位置”四字段组织本轮旅行。它优先承接玩家行动和正在进行的事情，允许平静的日常，不要求每轮新增人物、事故、冲突或选择题；移动时间、车辆状态、物品位置及人物认知按本轮需要提示。同一次请求先用完整资料规划至本轮行动结束，再按已定规划和条目适用条件筛选；不为保留物资扩写剧情或牵强安排用途。尚未发生的计划不成为已完成事实。

正文执行提示词由 DVS 提供，本卡不重复添加；只有输入增强及规划均开启且有可用规划时，规划和执行提示词才一起进入当前用户消息的发送副本。仅筛选、关闭或临时跳过时均不注入。角色生成条目的内容与筛选条件由作者单独维护，本节不替代相关条目的生成规则。

## 正文场景信息

地点变化或明显时间推进时，用 `<scene_info>` 输出当前场景的时间、地点、天气，不加“【场景】”标题。同一场景内的连续对话、小动作不用重复输出。

```text
<scene_info>
时间：2026-06-05 15:00
地点：湖边营地的房车停车位
天气：多云 26℃~20℃ 风力3级 降雨强度0mm/h
</scene_info>
```

时间使用 `YYYY-MM-DD HH:mm`，地点写具体位置。场景块表示这一段故事开始时的环境；世界表仍记录正文结束时的时间、地理范围和天气。

天气继续使用现有文本字段，格式为：

```text
{天气} {最高温度}℃~{最低温度}℃ 风力{风力等级}级 降雨强度{当前降雨强度}mm/h
```

温度为当日高低温，风力为等级，降雨强度为当前数值，无雨为 0。本轮经历的降雨另记在结算输入中，结束时放晴不会抹掉先前的降雨。

变量模型根据场景块及正文判断变化。现有 `<npc_角色名>` 标记继续用于角色信息更新。

## 本轮检查项

变量模型输出更新命令前，先按作者列出的检查项逐项核对本轮正文。例如正文写出停车、外出购物再回到车上，模型应分别核对主角与房车的结束位置、驻车和外出时长、明确收支及物资增减，再输出 `Analysis` 与 `UpdateCommands`。

检查项写在 [DVS-VAR-COT.txt](../世界书/DVS-VAR-COT.txt)，在 [index.yaml](../index.yaml) 中登记为启用的 `[DVS_VAR_COT]本轮变量核对` 条目：蓝灯、插入角色定义之前、顺序 116，位于六条 RULES（110～115）之后、`[DVS_DATA]`（120）之前，递归设置与 RULES 条目相同，不可被激活也不激活其他条目。条目用途的识别与合并规则见[选择世界书条目的用途](https://github.com/q3boy/st-sqlite-helper/blob/master/doc/dvs/指南/DVS作者使用手册.md#选择世界书条目的用途)。

| 检查项 | 主要内容 |
| --- | --- |
| 本轮范围 | 区分实际发生、计划、假设和历史回顾，不重复结算历史事件；空起点开场白按初始化规则处理 |
| 时间线 | 结合起点、`<scene_info>` 与正文确定结束时间；按顺序核对行车、驻车、外出时长，包括略过的睡眠和等候；检查重复计时、遗漏和跨日、跨周、跨月、跨年 |
| 结束位置与车况 | 主角、房车和 NPC 的结束位置分别核对，外出不把房车移到主角处；核对行政层级对应、车况、行车状态（行车／驻车）、拓展状态（收起／展开，行车时必须收起）和结束天气 |
| 本轮结算 | 按时间线整理活动、补给与额外消耗，检查中途补给前后的分段；区分日常消耗、额外使用车载资源和使用外部资源；核对持续补充，只输出结算输入 |
| 人物与主角信息 | 核对 NPC 新增或更新、互动造成的变化，同一事件不重复累计；离开不等于删除；资金只核对明确收支，粉丝变化核对作者规则规定的触发事件；玩家的行动意图与正文实际结果分开 |
| 物品变化 | 核对获得、使用、用尽、开封、丢弃和转交，区分公共物资与随身物品、部分取用与整份消耗；跨持有人转移时核对双方 |
| 输出核对 | 有依据的变化落实到正确的表、完整业务键和字段，不无故改写未变化字段；`Analysis` 覆盖每条 `UpdateCommands`，顺序与业务结果一致 |

检查项只引导模型核对，不规定业务结果。字段更新条件、单位、计数、允许估计范围、归属变化和资源计算分工都由 RULES 完整规定，停用 COT 后规则仍然完整。第 7 项只核对结论与操作是否一致，不要求模型再做一轮重复检查或改写前文。检查项与 RULES 的分工如下：

| RULES 位置 | RULES 保留的规则 | COT 补充的检查 |
| --- | --- | --- |
| 世界信息／日期时间 | 记录正文结束时间，格式 `YYYY-MM-DD HH:mm`，没有写明时根据剧情合理估计 | 跨日、跨周、跨月、跨年的核对 |
| 本轮结算／行程注释 | 行车、驻车、外出时长互不重复，覆盖本轮经过时间（含略过的睡眠、等候），依据场景块与正文合理估计 | 总时长、遗漏时间和重复计时 |
| 世界信息／地理与天气 | 行政层级对应、气候合理性和天气格式 | 结合结束位置和时间核对 |
| 房车信息与本轮结算 | 只读储量、活动分类、单位、补给成立条件、事件顺序、额外消耗与持续补充条件 | 补给分段和资源来源区分 |
| 角色信息 | 人设标签新增条件、好感依据与幅度、离开保留、观感与心声规则 | 同一事件不重复累计 |
| 房车物资与随身物品 | 各自数量规则、单位、转移、借用及删除条件 | 跨表转移的双方对应 |
| 主角信息 | 现有规则 | 收支、粉丝和行动意图的核对 |

模型在返回 JSON 的可选 `cot` 字符串中报告检查结果。DVS 不校验、不执行 `cot`，也不写库或作为事实依据，只随完整返回 JSON 保存在正文尾部供查看；油、水、电仍由 JS 按固定系数计算。检查文字不证明模型没有遗漏，效果要通过启用与停用 COT 的实际对比判断。条目使用见[提供本轮检查项](https://github.com/q3boy/st-sqlite-helper/blob/master/doc/dvs/指南/DVS接口与进阶用法.md#提供本轮检查项)。

## 临时结算输入

变量请求的表结构中增加虚拟表 `本轮结算`，字段为 `行程`（数组）和 `持续补充`（对象）。模型通过现有 `UpdateCommands` 输出这张表的数据，普通业务表继续按原规则更新。

以下 YAML 展示虚拟表的一行数据，实际模型输出使用 JSON。单位统一约定：时间为分钟，距离为公里，油、水为升，电为 kWh，降雨强度为 mm/h。

```yaml
行程:
  - 类型: 补给
    来源: 家附近的加油站
    资源: 油
    数量: FULL
  - 类型: 行车
    起点: 家附近的加油站
    终点: 湖边营地
    道路类型: 铺装
    距离: 120
    时间: 150
  - 类型: 驻车
    地点: 湖边营地
    时间: 180
  - 类型: 额外消耗
    行为: 洗车
    资源: 水
    数量: 100
  - 类型: 补给
    来源: 营地加水
    资源: 水
    数量: FULL
  - 类型: 外出
    地点: 营地附近的步道
    时间: 240
持续补充:
  太阳能时长: 300
  风电时长: 120
  雨水收集:
    时长: 90
    平均降雨强度: 2
```

行程按发生顺序排列。未发生的补给、额外消耗、持续补充项目省略，不要求每轮填写零值。数量使用非负数，允许小数；`FULL` 表示补满。

### 三种活动

| 类型 | 记录内容 | 含义 |
| --- | --- | --- |
| 行车 | 起点、终点、道路类型、距离、时间 | 房车移动，道路类型为铺装或非铺装；混合路面分段记录 |
| 驻车 | 地点、时间 | 房车停放，主要在车上生活、休息或在车旁活动 |
| 外出 | 地点、时间 | 房车停放，主角在外游览、购物等，车辆保持基本待机 |

三种活动的时长不重复，包括正文略过的睡眠、等候等时间。房车所在地和主角当前位置仍分别按正文更新，外出不会把房车移到主角所在地。

### 补给

每项记录 `来源`、`资源` 和 `数量`。资源为 `油`、`电` 或 `水`，分别对应油料、储备电力、储备水源；数量表示补入量，补满使用 `FULL`。一次涉及多种资源时分别记录。

JS 读取明确的资源和数量；资源无效、缺少数量或数量类型错误时报告错误，不将该项当作零补给。

来源使用简短文本，如“加油站”“营地水龙头”“备用柴油桶”。它帮助模型判断补给内容，不是分类枚举，JS 不通过解析这段文字关联库存或选择计算分支。

只记录已完成的补给；准备补给或仅连接设备不算已完成补给。

办理补给的时间包含在活动时长里，补给事件不再增加时间。补给在一段活动中途发生时，将活动分在补给前后，保留补满后继续消耗的顺序。

### 额外消耗

记录超出场景平均消耗的行为，例如洗车、大量外放电、从油箱抽油。每项填写 `行为`、`资源` 和 `数量`，资源同样为 `油`、`电` 或 `水`。数量为非负数，不使用 `FULL`；涉及多种资源时分别记录。

正文给了数量就记录该数量，没有数量就根据行为合理估计。JS 扣减这些额外用量。行为所用时间包含在活动时长中，不再新增一段时间。

普通做饭、洗澡、空调、柴暖等已包含在活动系数中，不逐项记录。洗车直接使用营地水管等外部资源时，不扣车载储备。

### 持续补充

| 项目 | 模型记录依据 |
| --- | --- |
| 太阳能时长 | 根据本轮时间、日照、天气和遮挡估计有效工作时长，夜间不计 |
| 风电时长 | 根据正文中风机的部署使用情况和风力估计工作时长 |
| 雨水收集 | 根据本轮降雨情况记录降雨时长和平均降雨强度，不计算集雨量 |

太阳能和雨水收集自动持续，不记录开启、停止状态。持续补充可以与活动同时发生，其时长不增加本轮经过时间。

## JS 计算

以下系数是游戏默认值，统一按整车计算，不输入人数，不单独计量空调、柴暖。

| 活动 | 油料消耗 | 电力消耗 | 清水消耗 |
| --- | --- | --- | --- |
| 行车 | 铺装 0.35 L/km；非铺装 0.50 L/km | 0.5 kWh/h | 2.5 L/h |
| 驻车 | 0.1 L/h | 0.8 kWh/h | 2.5 L/h |
| 外出 | 0 L/h | 0.1 kWh/h | 0 L/h |

行车油耗按距离计算，其余按时长计算。驻车油、电系数包含日常温控等设备的平均消耗。

| 补充项目 | 简化计算 |
| --- | --- |
| 行车充电 | 行车小时 × 1.0 kWh/h |
| 太阳能 | 有效工作小时 × 1.5 kWh/h |
| 风电 | 工作小时 × 0.6 kWh/h |
| 集雨 | 降雨小时 × 平均降雨强度 × 14㎡ |

集雨面积按厢体投影 `6.5 × 2.2 = 14.3㎡` 四舍五入取整为 **14㎡**。1 mm 降雨落在 1㎡ 上为 1 L 水，不另外设置集雨效率。行车、太阳能、风电采用固定有效补电系数，不再输入效率或负荷。

计算顺序：

1. 从本轮起点数据读取油、水、电。
2. 按行程顺序计算活动消耗、补给和额外消耗。行车电耗与行车补电合并计算。
3. 轮末统一补入太阳能、风电和雨水。
4. JS 统一处理储量范围：各项补给和消耗不会使储量超出 0 与容量之间，油 1000 L、电 72 kWh、水 1000 L。油、水保留 1 位小数，电保留 2 位小数。模型不计算剩余容量或可补入上限。
5. 删除本轮结算虚拟表，只保存业务表及计算后的储量。

持续补充采用本轮合计、轮末加回，因此不精确区分途中已经满箱、满电时溢出的部分。这是该简化结构的精度限制。

房车物资按桶、袋、盒、包、份、件等整份计数，数量为非负整数。未用尽的开封包装仍计一份，部分取用只按正文更新说明或状态，不把升数换算为小数桶数；用尽整份、丢弃或转交整份时扣减数量。完整规则见[房车物资规则](../世界书/DVS-RULES_房车物资.yaml)。本方案不新增来源分类、来源文本解析、自动库存换算或逐桶状态处理。

房车物资数量列声明为 `INTEGER`，并用数据库约束拒绝小数和负数。此建表DDL用于新数据库；已有聊天不会重复执行已完成的DDL，不会自动修改旧列或取整旧数量。

## 接入边界

`本轮结算` 是变量请求的虚拟表，与世界信息、房车信息等业务表同级，不是房车行中的字段。作者提供其表结构与记录规则，模型照常在 `UpdateCommands` 中用 `table: "本轮结算"` 定位，不在输出协议顶层增加结算字段。

1. 变量请求提供真实业务表与本轮结算虚拟表的结构。
2. 按现有补丁协议在内存中形成各表数据，虚拟表的对象、数组保持原生 JSON 值，不经过 SQL TEXT 转换。
3. `preUpdate` 读取 `newTables.本轮结算`，按系数计算业务表的储量。
4. 回调执行 `delete newTables.本轮结算`，再返回数据。
5. DVS 检查最终数据只包含真实注册业务表及合法字段，然后生成 SQL、写库。没有清除的虚拟表报错，不静默丢弃。

虚拟表仅属于本次变量更新，不从历史楼层继承，不建立物理表、数据库列或楼层索引，不增加回调参数或单独传递通道。`[DVS_DATA]` 仍提供完整业务起点。

虚拟表通过 `DVS.register({ virtualTables: { 本轮结算: { keys: [], fields: { 行程: 'array', 持续补充: 'object' } } } })` 声明，以 `keys: {}` 定位至多一行。公开用法见[虚拟表输入与写库前计算](https://github.com/q3boy/st-sqlite-helper/blob/master/doc/dvs/指南/DVS作者使用手册.md#虚拟表输入与写库前计算)。
